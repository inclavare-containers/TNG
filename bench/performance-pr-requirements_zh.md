# 性能优化 PR 描述规范

本文件是英文规范 `performance-pr-requirements.md` 的中文配套说明。Agent 创建或更新任何声称性能收益的 PR 时，必须读取并遵守该规范，并在最终代码、提交、配置或压测发生变化后重新核对。PR 标题和正文用英文；已有压测执行规则继续生效。

## 必需结构

依次使用 Summary、Changes and configuration、Benchmark setup、Results and tradeoffs、Validation and remaining work、Full benchmark comparison。正文简洁、独立可读；每个场景必须有默认展开的档位计数表和默认折叠的完整数据表；额外小结表或图可选，不能替代完整表。

- 摘要交代问题、改动、实测结果、遗留差距和主要代价。数字必须明确协议模式、证明设置、连接行为和并发范围。
- 配置说明核对代码中的默认值、未设置行为、单位、边界、合法性、适用范围和示例；区分每连接流数与连接数、软限制与硬限制、默认与可选行为。不按已过时的提交数量或 agent 工作经历组织正文。
- 压测设置记录前后精确源码版本、脏补丁、构建/二进制身份、实际参数、依赖提交、run ID、硬件网络、工具版本、预热、时长、轮数、聚合方法、负载大小和并发矩阵。发布版本不足以定位源码；未知身份必须标注未验证，不能编造 SHA。相同条件可列一次或链接完整保留的 manifest；差异表不能替代复现信息。使用可公开的主机角色和命令，不能泄露私有地址、凭据或内部 SSH 别名。
- 收益与代价分别说明相对优化前及相对 raw/HAProxy/stunnel 的结果。范围必须说明并发条件；摘要与整表一致，并披露回退、CPU/内存成本和控制模式结果。
- 验证区分实际通过、失败、未执行；区分观测事实、profiling 支持的原因和假设。没有证据不能断言瓶颈或未来优化必然消除差距。只有满足 issue 验收条件才写 Closes，否则用 Related to 并列出遗留项。

## 必须保留完整表

每个实验都必须有完整脚本生成的对比报告，保留所有实测场景、模式、控制负载、并发、指标及不利数据；已采集的延迟分位数、成功率/错误、CPU 和内存均需保留，不得裁剪坏行或用精选示例替代。完整报告以 PR 评论形式维护而非正文（GitHub 正文有大小限制装不下）：每份报告是一个 `--fold` 生成的整报告 `<details>` 块，由 `bench/pr-report-comments.sh` 按 summary 行匹配后原地更新，绝不重复发帖。正文用紧凑哈希区间行链接各评论：主报告 `Full benchmark: [<base>...<head>](url)`，每个消融步骤 `Ablation step N: [<a>...<b>](url) (对所做改动的简短自然语言描述)`。报告内部每个场景完整大表仍各自放在标注清楚的 `<details>` 默认折叠内，档位计数表保持折叠块外可见。按已有产物策略保留生成报告与原始数据。

用 `bench/gen-report.sh --compare` 生成，不能手工重抄或修改数值表。需要改格式时修改生成器并用保留数据验证；不要手工修改生成证据。

## 比较基准与五档标记

保留相邻优化前/优化后行及全部指标。实验指标单元格使用下表五档方向感知标记，由 `bench/gen-report.sh --compare` 直接生成；比较同场景、同模式、同并发、同指标的前后原始数值，不按 raw/HAProxy 或已四舍五入的 vs-raw 百分比分类。

| 标记 | 档位 | 相对优化前的变化 |
|---|---|---|
| 🟢 | 改善 | 向有利方向变化超过 1% |
| ⚪ | 基本持平 | 绝对变化不超过 1% |
| 🟡 | 轻度劣化 | 向不利方向变化超过 1%，不超过 5% |
| 🟠 | 中度劣化 | 向不利方向变化超过 5%，不超过 15% |
| 🔴 | 重度劣化 | 向不利方向变化超过 15% |

生成器用未舍入数据计算 `(after-before)/before*100`。吞吐/RPS/成功率越高越好，延迟/CPU/RSS/错误率越低越好。阈值仅用于展示，不代表噪声带、统计显著性或验收通过。CPU/RSS 上升属于资源代价，不自动意味着优化失败；效率结论需单位 CPU 吞吐或同工作量资源对比支撑，明确组件、进程聚合和 CPU 单位。

成功率列在五档展示中也使用上述相对变化公式；正文区分百分比与百分点。即使落入持平档，新增错误或成功率下降仍需明确点名，不能用分类掩盖正确性或可靠性问题。另有验收阈值需单独说明，不能暗中改变分档阈值。

绝对数保留实测值，原括号百分比明确相对表中 raw，并说明 raw 来自优化前还是对应 run。HAProxy 比值写明 of/vs HAProxy；彩色标记表示相对优化前。额外前后变化百分比单独标注，不能替换原 vs-raw 数值。

缺失/非有限测量值、无法匹配的前后项、零分母导致的未定义变化属于数据完整性问题，不是第六档。说明具体问题并修复对比，或在发布完整分类摘要前明确证据不完整。不能增加 N/A 档位、编造百分比、静默删项或归为持平。仅作参考行中按设计未采集的指标不属于比较总体。

## 每个场景必须有计数表，大表默认折叠

每个场景依次展示：场景标题、简短主要发现、默认展开的档位计数表、图例及统计范围、默认折叠的完整前后数据大表。整表必须留在 PR 正文，不能用外链或精选行替代。

计数表要求：

1. 第一列为 `Change class`（变化档位）。
2. 第二列为 `Count (%)`（总计数及百分比）。
3. 后续列与对应大表的指标表头、单位、顺序完全一致，不合并为延迟/资源等指标组；不包含 Streams/Conns/Workload 等标识列。
4. 五档行依次为 🟢 改善、⚪ 基本持平、🟡 轻度劣化、🟠 中度劣化、🔴 重度劣化，最后为 Total 总计行；不设 N/A 档位。

每个指标单元格为落入该档的“模式 × 并发”前后比较项整数个数。每个实验指标单元格只计一次，不重复统计 baseline，也不统计仅展示一次的 raw/stunnel/HAProxy 参考行。包含所有参与前后比较的 TNG/控制模式，说明模式及并发范围；补充的控制负载前后表若不属于主表范围，应单独统计。

每档 Count 为该行各指标计数之和，百分比为 `Count / 全部可比较指标项数 × 100`，统一保留一位小数。总计行列出各指标比较项数，以及整体 `N (100.0%)`。舍入后档位百分比之和可能为 99.9% 或 100.1%，不能改计数凑整。每行、每列及总计一致，全部应比较项均有完整测量，两项均由生成器校验。没有比较项的场景是错误，不能写 `0 (100%)`。

本节全部内容为生成器直接输出：`bench/gen-report.sh --compare` 用同一份未舍入数据一次生成标记、计数表和 Count (%)，并自行校验一致性，无需任何人工拼装。上述格式是生成器输出必须持续满足的契约：格式需要变更时改生成器及其测试，不改已发布表格。

## 报告边界、结构与元数据

每份生成报告恰好两章：`Benchmark setup`（编号普通行 1. Test Environment、2. Test Conditions、3. Test Tool Versions、4. Test Methodology——加粗行而非标题，完整元数据在默认折叠块内）和 `Results`（各场景小节）。以评论形式呈现的报告（`--fold`）不带顶层标题：折叠块 summary 行即标题。环境表只渲染主机、内核、CPU、内存、TNG 版本和 TNG 源码版本；manifest 时代的字段（二进制校验和、源码状态、脏树、构建命令/环境、构建时间、run ID）不渲染——源码版本即身份。

`1. Test Environment`、`2. Test Conditions`、`3. Test Tool Versions` 每章必须同时展示：

- 默认展开的差异表，表头 `Item | Baseline | Experimental`，列出全部变化项。没有差异时在折叠块外显示 `No differences.`，这句话不能替代完整表。
- 紧接其后的默认折叠 details 块，展示该章实际完整元数据表，表头也为 `Item | Baseline | Experimental`，包括全部未变化项。summary 分别标明 Full test environment、Full test conditions、Full test tool versions。只在一侧存在的字段也保留，缺失元数据明确标注。差异表与完整表从同一采集数据生成，字段顺序及值一致；不能用外链或差异表替代完整表。敏感值一致脱敏，不能编造公开测量值。

`4. Test Methodology` 标题保持可见，固定方法说明放入默认折叠的 `<details><summary>Test methodology and metric definitions</summary>`。比较图例放在对应表附近，不藏进方法块。固定内容由生成器统一维护，不要求每个 PR 重写，但必须与实际运行一致；采样、聚合、拓扑或工具与固定方法不同，差异需直接展示，并修正实际方法说明。模板不能声称并未实际满足的条件。

## 实测二进制版本必须可信

`git unknown`、缺失 revision、从报告生成机器推测 revision 都属于身份/采集失败，不能作为最终压测版本。发布性能结论前应排查版本采集，或从保留的构建/部署 manifest 证明身份，再用核实后的元数据重新生成报告。不能用当前 HEAD 替换 unknown，不能没有证据就改历史元数据。无法恢复历史版本时，保留原始证据并标为未验证；作为可复现的最终证据前需重新记录身份并压测。

优化前后均分别记录 ingress 与 egress 的二进制身份：构建时完整源码 SHA、脏工作区/补丁身份、构建参数和二进制校验和；部署后核对校验和并关联 run ID。在压测主机当前目录执行 git 成功，也不证明已部署二进制来自该版本；显式传入 TNG_GIT 也需与部署构建 manifest 一致，未验证的环境字符串不能充当证据。报告生成器应检测版本缺失/unknown 及两端不一致，输出可操作诊断，不能静默当成最终可复现结果。故意混合版本的测试需明确两端版本。

## 证据与收益归属

组合优化结果标为组合收益，列出准确测试组成。只有隔离对比（如优化前、仅前置优化、前置优化加本次改动）才能归因单项收益；否则明确未隔离。拆 PR 或 rebase 后同时核对最终 diff、标题、依赖和实测二进制。

没有覆盖所声称范围的证据，不能写无回退、不变、噪声范围内、持平或目标达成。固定显示容差不等于实测噪声带。异常保留数字，原因未查明就写未知；影响结论的回退、内存增长、基线漂移或尾延迟异常需调查或复测。证据不足标为初步结果，不能隐去异常或编造确定结论；区分快速迭代与最终评估并披露限制。

## 多优化 PR：每步优化的消融报告

一个 PR 内落了多个可拆分的优化（每个 commit 或 commit 组是可独立成立的改动）时，逐步消融证据是必需项而非可选项：

- 主对比报告（PR head vs PR 基线）仍是 PR 级结论，保留其必需的展开结构。
- 消融章节必须额外为**每个优化步骤**各放一份完整对比报告：第一步 = PR 基线 vs 第一步树，第 N 步 = 第 N-1 步树 vs 第 N 步树。报告由同一 `bench/gen-report.sh --compare` 流水线生成，格式与主报告一致（元数据差异表、五档单元格标记、每场景计数表、完整数据表）。纯测试 commit 和纯工具 commit 不出报告，在消融汇总表中如实标注。
- 每份步骤报告整体包在一个默认折叠的 `<details>` 块内（无 `open` 属性），summary 写明步骤名、两臂的源码版本和 run ID。整份报告折叠，这一点与主报告不同（主报告的主要发现和计数表保持可见）。
- 正文只保留紧凑链接行；所有数字都在评论内报告里。正文不放手写的分步汇总表、复合性说明或交叉核对段落：那些只是评论报告已展示内容的重复。
- 每份步骤报告是独立测量，有自己的 run 身份和二进制 manifest；不得把它的数字混入主矩阵叙述。手搓的步骤表不满足本规则；生成器尚不支持渲染消融两臂时，先扩展并用留存输入数据验证，与主报告同等要求。

## 已固化到脚本的规则与仍需人工核对的部分

`bench/gen-report.sh --compare` 现已自动生成五档单元格标记、与大表表头一致的各指标计数表及 Count (%)，分档和计数共用同一函数与数据。它同时生成报告分隔线、展开的元数据差异及折叠的完整表、分组且折叠的方法说明、展开的场景主要数值变化与紧凑图例、折叠完整大表、单独的参考/控制负载前后漂移对比。无需手改表格或手工计数；自动数值摘要只指出不利变化，不编造原因。

生成器拒绝不可读/格式错误 JSON、空或不支持的结果、非法指标范围、缺失模式/并发配对、缺失/非有限指标、未定义百分比分母，不能静默丢项或新增 N/A 档。它校验前后两端身份；故意混合版本需要显式 `--allow-mixed-versions`。校验失败返回非零且不覆盖已有报告。使用报告前必须检查命令退出状态，保留下来的旧文件不代表新报告已成功生成。

新压测需用 `bench/record-build.py` 执行构建并生成身份 manifest，将其作为 `<binary>.build.json` 随二进制部署（或设置 TNG_BUILD_MANIFEST），压测脚本还需一起部署 report_support.py。client/server 在预检及采集时核对部署二进制校验和、版本与 manifest；TNG_GIT 不再回退读取压测机 HEAD，若显式设置则必须等于 manifest 中完整 SHA。采集还记录实际配置校验和、预热、mux 设置及 run ID。

命令与离线测试见 reporting.md / reporting_zh.md。历史数据缺少可信构建 manifest 时，只能用 `--allow-unverified` 生成醒目标注 PRELIMINARY / UNVERIFIED 的初步报告；它不修复版本身份、不豁免结果完整性校验，也不授权将该报告作为最终证据。不能为历史二进制编造 manifest。

仍需 agent/reviewer 判断：改动与瓶颈解释、组合收益隔离、最终 PR head 与实测构建的关系、实际验收条件、异常诊断/复测、源码/配置语义、正文结论与生成数据一致性。不能在成功率持平或 CPU 劣化时声称所有指标改善；补充 A/B 测量需注明独立 run 身份和数据，不能混用主矩阵数字。方法按拓扑、负载、延迟/成功率、资源采样、比较口径分组；详细方法折叠，外部只留紧凑图例。

## 正文一致性与方法章节呈现

发布或更新 PR 正文前，对照最终生成报告逐项核对：

1. **准确限定改善范围。** 只有所声明范围内全部可比较指标均为 🟢，才能写“所有指标改善”。成功率持平应写持平，资源劣化必须披露。优先明确写“RPS 和延迟改善，成功率持平，CPU 在这些并发下上升”，不能把整体收益扩写为每个单元格都改善。
2. **每个例子可追溯到具体数据集。** 正文引用的前后数字、资源示例和范围必须与整表中的场景、模式、并发、指标、单位及 run 配对一致。专门 A/B 实验或另一轮复测需有独立 run ID 和明确标注，不能静默混用其数字与主矩阵。正文和表格不一致时先核实来源，再改正文或从可信输入重新生成报告，不能改实测表格迎合摘要。
3. **无回退结论必须限定范围。** 有指标劣化时不能笼统写“其他指标无回退”。需说明范围并披露不利项，包括控制模式及尾延迟回退。疑似噪声仍是需解释或复测的观测，不能仅凭其他指标改善就排除。
4. **方法章节在视觉上收拢。** 保留可见的 4. Test Methodology 标题，拓扑、负载、延迟/成功率定义、资源采样及详细比较规则分组置于默认折叠 details 内。主题间用空行，适当用短列表，不在段内任意硬换行。折叠块外只在对应结果表旁保留紧凑图例和计数口径，不能紧接冗长、重复的方法或比较说明。核对实际 details 开闭标签及无 open 属性；纯文本抓取会包含折叠内容，不能据此断言页面未折叠。

即使所有表格由脚本生成，也必须核对最终 PR 前文。生成报告保留为证据，正文应如实反映证据。
